# 3.3 Sprint Cycles

## Overview

The Disaster Preparedness Training and Simulation System follows Agile Scrum methodology with structured sprint cycles to ensure iterative development and continuous improvement. Each sprint produces a usable product Increment that can be demonstrated to LGU stakeholders.

## Sprint Structure

Each sprint cycle follows a standard Scrum workflow:

1. **Sprint Planning** — select Product Backlog items and create the Sprint Backlog
2. **Daily Stand-ups** — short coordination on progress, blockers, and next steps
3. **Development & Testing** — implement stories against the Definition of Done
4. **Sprint Review** — demo the Increment to stakeholders
5. **Sprint Retrospective** — identify process improvements for the next sprint

## Sprint Duration

- **Sprint Length**: 2 weeks per sprint (extendable to 3 weeks for heavy integration work)
- **Sprint Planning**: First day of each sprint
- **Daily Standups**: Daily 15-minute meetings
- **Sprint Review**: End of sprint demonstration
- **Sprint Retrospective**: Post-sprint improvement session

## Ceremonies and Roles

| Role | Responsibility |
|------|----------------|
| Product Owner | Prioritizes Product Backlog; accepts Increments |
| Scrum Master / Project Lead | Facilitates ceremonies; removes blockers |
| Development Team | Designs, builds, tests, and documents features |
| Stakeholders (LGU) | Provide feedback during Sprint Reviews |

## Definition of Done

A task is considered Done when:

1. Code is written and reviewed
2. Unit / feature checks pass for the sprint scope
3. Integration checks pass where partner APIs are involved
4. Documentation and backlog status are updated
5. Feature is verified on staging or production-like environment
6. Product Owner approval is received in the Sprint Review
